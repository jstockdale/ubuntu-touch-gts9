# Ubuntu Touch: gts9wifi (SM-X710) → gts9uwifi (SM-X910) Port Plan

Prepared 2026-08-03 from direct analysis of `ubuntu-touch-gts9wifi-24.04-2.x.zip`
(built 2026-07-29) and the `azkali-samsung/gts9` GitLab source tree.

## 0. Verdict

The port is very favorable, and materially easier than a from-scratch bring-up. The
24.04-2.x bundle's architecture is close to model-agnostic at the kernel level:
the flashed device tree is the **generic `qcom,kalama` base** (msm-id 0x207 v2,
zero Samsung strings), all board description comes from **DTBO overlays**, the
tablet's stock `dtbo` partition is **retained** (`deviceinfo_skip_dtbo_partition=true`),
and the kernel is built from Samsung's family source with the **generic
`vendor/kalama-gki_defconfig`** rather than a per-model config. Independent
corroboration that the family kernel is cross-model: the XDA NinjaSU project builds
one kernel from SM-X710 source and it runs on SM-X910 and SM-X810.

The genuinely device-specific surfaces are exactly five: (1) the stock donor
partitions inside `super` (vendor / vendor_dlkm / odm / product / system_ext /
system_dlkm), (2) the prebuilt DTB + DTBO checked into the port repo, (3) the
hand-curated first-stage `modules.load` lists, (4) the UT rootfs `overlay/`
config files (deviceinfo yaml, audio policy, sensorfw, repowerd waits), and
(5) possibly panel/touch driver source in the kernel + display techpack if the
Ultra's ICs are not already covered by the gts9wifi drop.

Realistic expectations: display, touch, GPU, Wi-Fi/BT, audio, sensors, S Pen,
charging – high confidence. Cameras – the hardest subsystem on any Halium port;
main rear + main front are the plausible target, and the two ultrawides (rear UW,
notch front UW) will almost certainly not be reachable from the UT camera stack
without extra HAL plumbing. "Complete support for multiple cameras" should be
treated as a stretch goal, not a baseline. Details in §6.

## 1. What the 24.04-2.x bundle actually is (verified findings)

### 1.1 Installer flow (`META-INF/.../update-binary`, plain `/sbin/sh` script)

- Gates on `ro.product.device == "gts9wifi"` → for the Ultra this must become
  `gts9uwifi` (generated by `scripts/make-flashable.sh`, so it's templated).
- `dd`-flashes `boot`, `init_boot`, `vendor_boot`, `vbmeta` to
  `/dev/block/by-name/<part>$SLOT` (slot suffix read but empty – Samsung A-only,
  confirmed by unsuffixed LP partition names).
- Streams `super.img.zst` through `zstd -d --long=27` straight onto `super`
  (bundled static `zstd` binary as fallback for TWRP environments without it).
- Notably absent from the flash list: `dtbo`, `vendor`, and every other stock
  partition – the device keeps its stock DTBO and modem/firmware partitions.

### 1.2 Image inventory

| Member | Size | Format | Contents |
|---|---|---|---|
| `boot.img` | 32 MiB | boot v4 | kernel only (gzip Image, 38 MB raw), empty cmdline, OS 13, SPL 2025-05 |
| `init_boot.img` | 8 MiB | boot v4 | LZ4 cpio – standard **halium-generic initramfs** (`scripts/halium`), device-agnostic |
| `vendor_boot.img` | 13.8 MiB | vendor_boot v4 | one platform ramdisk (LZ4 cpio: **only `/lib/modules`**, 415 .ko) + DTB 452 KB + bootconfig |
| `vbmeta.img` | 4 KiB | AVB | `flags=0x2` – verification disabled; reusable as-is on the Ultra |
| `recovery.img` | 104.5 MiB | boot **v2** | same kernel + 26.9 MB gzip ramdisk (unified TWRP-style recovery) + `recovery_dtbo` (4 overlays) + same DTB |
| `super.img.zst` | 2.97 GB | zstd(raw img) | see 1.5 |
| `zstd` | 1.6 MB | static binary | installer fallback |

### 1.3 Kernel

`Linux version 5.15.153`, clang 14.0.0 (r450784e per deviceinfo), built
2026-07-29 on GitLab CI (`azkali-samsung/gts9/ubports/samsung-gts9`, project id
58785718 – visible in the build banner). Built from
`kernel-samsung-gts9wifi.git` branch `android13-5.15-halium` with
`vendor/kalama-gki_defconfig halium.config`.

The halium patch stack on that branch is compact (~40 commits) and almost
entirely: `halium.config` knobs (LSM ordering apparmor/selinux, netfilter for
Waydroid, squashfs for snaps, `net.ifnames=0`), USB role-switch/dwc3-msm host
ordering fixes, `usb_notify` OTG vbus gating, one DTS patch
(`pmk8350: allow rtc set-time`), and reserved-memory experiments. **The current
HEAD is a revert of "reclaim the cont_splash framebuffer"** – which is very
plausibly what un-broke the 2.x splash hang observed on the X710; the 2026-07-29
build includes that revert. Worth confirming this build boots your X710 before
using it as the port base.

### 1.4 Device tree scheme (the key architectural fact)

- `vendor_boot` DTB: single FDT, model = "Qualcomm Technologies, Inc. Kalama v2
  SoC", compatible `qcom,kalama`, `qcom,msm-id = <0x207 0x20000>`,
  `qcom,board-id = <0 0>`. **No** gts9 strings. Maintained as source in the repo
  (`vendorboot/vendor_dts` → `vendorboot/vendor_dtb`).
- Board description arrives via **DTBO overlays**. Normal boot: ABL applies
  overlays from the tablet's **stock `dtbo` partition** (per-model, untouched by
  the installer). Recovery boot: overlays come from `recovery_dtbo` embedded in
  `recovery.img` – currently 4 gts9wifi overlays: `Samsung GTS9WIFI PROJECT
  (board-id 00 / 01 / 02 / 04)`.

Consequence: on an X910, the same generic base DTB gets the **Ultra's own stock
overlays** applied at boot – panel, touch, cameras, battery are described
correctly by the device itself. The two things that must change are the
`recovery_dtbo` (swap in X910 stock `dtbo.img`) and, if the stock base DTBs
differ between models, the base `vendor_dts` (verify by extracting stock X910
`vendor_boot` – see §5 Phase 0; there is a real chance they are byte-identical,
since Samsung's whole scheme is common-base + per-board overlays).

### 1.5 super layout (LP metadata parsed from the image)

Group `ubuntu`, 2 metadata slots, block device 10.84 GiB:

| LP partition | Size | Source |
|---|---|---|
| `system` | 4500 MiB | **UT rootfs** (`out/ubuntu.img`: UBports 24.04-2.x android9plus rootfs + device tarball) |
| `system_ext` | 138 MiB | stock-derived |
| `system_dlkm` | 0.3 MiB | stock-derived |
| `product` | 1285 MiB | stock-derived |
| `vendor` | 1646 MiB | stock-derived (gts9wifi) |
| `vendor_dlkm` | 34 MiB | stock erofs, **rebuilt** with halium-kernel .ko swapped in (`swap-vendor-modules.sh`) |
| `odm` | 0.8 MiB | stock-derived |

The six non-system images ship in
`download.azka.li/samsung/tab-s9/firmware/ubuntu-touch-kalama-firmware-v.tar.xz`
(2 GB). These are gts9wifi partitions, presumably pre-edited from stock for
halium (the exact edit set is not published; determine it by diffing against
pristine X710 stock of the same build – §5 Phase 2).

### 1.6 First-stage modules (vendor_boot ramdisk)

415 modules present; `modules.load` = 124 (normal boot), `modules.load.recovery`
= 416 (everything). Both lists are **hand-curated in the repo**
(`vendor-ramdisk-overlay/lib/modules/`). Board-relevant entries observed:

- Display: `msm_drm.ko` (Samsung display techpack incl. ss_dsi panel driver,
  built from the `display-drivers` fork), `panel_event_notifier`,
  `sec_panel_notifier_v2`, `qpnp-amoled-regulator`, `lcd.ko`
- Touch: **`stm_ts_fts1b90a.ko`** – the X710's STM FTS touch IC driver.
  The Ultra's touch IC is the single most likely first-stage delta (see §7)
- Power/charging: `sec-battery`, `sec-direct-charger`, `sm5714`
  (MUIC/charger/fuelgauge), `sm5440-charger`
- Audio amps: `snd-soc-cs35l43-i2c`, `snd-soc-cs35l45-i2c` (Cirrus, quad-speaker)
- Misc Samsung: `stm32_pogo_v3` (pogo keyboard), `hall_ic`, `a96t396` (grip),
  `fingerprint.ko`/`fingerprint_sysfs.ko`, full `sec_qc_*` debug family
- Wi-Fi platform per deviceinfo: `qca6490` (same silicon family on the Ultra;
  both are Wi-Fi 6E on SM8550-AC)

All 415 modules were built from the gts9wifi source drop under the generic
kalama defconfig – no Ultra-specific strings exist anywhere in the bundle.

### 1.7 Build pipeline (from `samsung-gts9` repo, branch `halium-13`)

`build.sh` → clones halium-generic-adaptation-build-tools (branch
`personal/azkali/gts9-integration`) + 10 techpack repos (`display-drivers`,
`graphics-kernel`, `camera-kernel`, `audio-kernel`, `wlan`, `bt-kernel`,
`eva-kernel`, `mm-drivers`, `mmrm-driver`, `securemsm-kernel`, all
`android13-5.15-halium`) → builds kernel + DLKMs → assembles
boot/init_boot/vendor_boot/recovery from `deviceinfo` + `vendorboot/` prebuilts
→ fetches UBports rootfs → produces `ubuntu.img` → downloads the firmware
tarball → `swap-vendor-modules.sh` (erofs rebuild of vendor_dlkm with fresh
.kos, SELinux xattrs preserved) → `scripts/super.sh` (lpmake, `SUPER=11643387904`)
→ `make-flashable.sh` → zip. CI zstd-compresses ubuntu.img and uploads.

## 2. Hardware delta: SM-X710 → SM-X910

Same SoC (Snapdragon 8 Gen 2 for Galaxy, SM8550-AC "kalama"), same Wi-Fi 6E /
BT class, same UFS/storage class, quad speakers and S Pen on both. Differences
that matter to the port:

| Subsystem | X710 (Tab S9) | X910 (Tab S9 Ultra) | Port impact |
|---|---|---|---|
| Display | 11" 2560×1600 AMOLED 120 Hz | 14.6" 2960×1848 AMOLED 120 Hz, **notch** | Different panel IC/timings → DTBO (stock, free) + ss_dsi panel driver source must exist in display-drivers build (§7.1); larger cont_splash carveout in DT |
| Touch | STM FTS1B90A (`stm_ts_fts1b90a`) | TBD – read from stock X910 `modules.load` | Likely different first-stage module + driver source (§7.2) |
| Rear camera | 13 MP | 13 MP + 8 MP UW | vendor HAL delta (stock donor handles it) |
| Front camera | 12 MP | 12 MP + 12 MP UW (notch) | same |
| Fingerprint | (family sec fingerprint stack) | under-display optical | biometryd integration is its own project; fork exists in the group |
| Battery | 8400 mAh | 11200 mAh | sec-battery params via stock DTBO/vendor – free |
| RAM | 8/12 GB | 12/16 GB | none |

## 3. Complete gts9wifi-specific surface inventory (what must change)

1. **`kernel-samsung-gts9wifi`** – possibly gains Ultra touch/input driver
   source + Kconfig (decision in §5 Phase 1); DTS untouched if base DTBs match.
2. **Techpack forks** – `display-drivers` (Ultra panel source/config, §7.1),
   possibly `audio-kernel`/`camera-kernel` config deltas. Determine by diffing
   Samsung's X910 drop against the X710 drop; expected small and additive.
3. **`samsung-gts9` repo** (fork → `samsung-gts9u` or a codename-parameterized
   branch):
   - `deviceinfo`: codename `gts9uwifi`, name "Tab S9 Ultra 14.6'",
     `recovery_partition_size` (verify from X910 PIT/stock recovery.img size –
     do not assume 109576192), density (239 ppi → keep xxhdpi or drop to xhdpi,
     cosmetic), `system_partition_size` fine, `SUPER` size (verify X910 super
     partition size – likely identical but check PIT).
   - `vendorboot/vendor_dts|vendor_dtb`: regenerate from **stock X910
     vendor_boot** DTB + reapply the one halium DTS patch (pmk8350 rtc). If
     byte-identical to X710's, keep as-is.
   - `vendorboot/dtbo`: replace with **stock X910 `dtbo.img`**.
   - `vendorboot/bootconfig*`: verify against stock X910 vendor_boot bootconfig
     (currently generic: `androidboot.hardware=qcom`, memcg, dwc3 – likely
     unchanged).
   - `vendor-ramdisk-overlay/lib/modules/modules.load{,.recovery}`: rebuild from
     **stock X910 vendor_boot ramdisk's own lists** (authoritative), merged with
     the halium additions Azkali made for gts9wifi (diff his lists vs stock X710
     lists to isolate those additions).
   - `overlay/`: every `gts9wifi`-named file duplicated/adapted –
     `deviceinfo/devices/gts9uwifi.yaml` (screen size/DPI/orientation values for
     14.6" 2960×1848), pulse `audio_policy_configuration.xml` + volumes (source
     from **X910 stock vendor**), `sensorfw` conf, NetworkManager MAC conf,
     apparmor mountinfo abstraction, repowerd backlight/battery wait overrides,
     lsc-wrapper hwc2/overlay confs (re-test whether `disable-overlays` is still
     needed on the Ultra's SDE pipeline), EFS mount units, adbd restart conf.
   - `.gitlab-ci.yml` / `make-flashable.sh` output naming + update-binary gate.
4. **Firmware donor tarball** – new `ubuntu-touch-kalama-firmware-gts9u.tar.xz`
   built from stock X910 partitions with the same edit set as the gts9wifi one
   (edit set determined empirically, §5 Phase 2).
5. **Install collateral** – Odin-flashable Ultra recovery tar + vbmeta for the
   initial TWRP entry (vbmeta.img reusable as-is).

## 4. Prerequisites

- **An unlockable SM-X910.** Per your prior research: One UI 8.5 burns fuse
  bit 6 permanently; the target is a unit still on pre-bit-6 stock (or dead
  stock sourced accordingly). Standard Samsung ritual applies: OEM unlock in
  developer options, download-mode unlock, expect KG/RMM prenormal timing games,
  and a full wipe.
- **Stock X910 firmware** matching a sane patch level (the bundle's boot SPL is
  2025-05; keep the device's installed stock ≥ the custom images' SPL to stay
  clear of any ABL rollback pickiness). Needed pieces: `vendor_boot` (base DTB +
  stock modules.load), `dtbo`, `super` (donor partitions), `recovery` (size
  reference), PIT (partition sizes).
- **Samsung opensource drop for SM-X910** (opensource.samsung.com) – kernel +
  techpacks, for the touch/panel/audio source and defconfig diff. The family
  drops are near-identical; the X710 drop already builds a kernel that runs on
  the X910 (NinjaSU evidence), so this is a source of *deltas*, not a new base.
- Bench: Odin (or Heimdall if it cooperates with this generation – verify),
  `lpunpack`/`lpmake`, `fsck.erofs`/`mkfs.erofs`, the port repo toolchain.

## 5. Phase plan

### Phase 0 – Donor acquisition + keystone experiment (no new code)

1. Pull stock X910 firmware; extract `vendor_boot`, `dtbo`, `super`, PIT.
2. **Compare stock X910 vendor_boot DTB against `vendorboot/vendor_dtb`
   provenance** (i.e., against stock X710's base DTB). If identical → the base
   DT is settled. If not → decompile, diff, port the pmk8350 rtc patch onto the
   X910 base.
3. Extract stock X910 vendor_boot ramdisk `modules.load` – this names the
   Ultra's touch driver and any other first-stage deltas. This single file
   answers most of §7.2.
4. **Keystone test:** repack the existing `recovery.img` with (a) X910 stock
   `dtbo.img` as `recovery_dtbo`, (b) X910 base DTB if it differed, (c) a
   modules.load.recovery adjusted per step 3 – adding the Ultra touch .ko built
   from the X910 drop if it's not among the 415. Odin-flash to the unlocked
   X910 with the existing `vbmeta.img`. If recovery UI comes up with working
   touch on the 14.6" panel, the family-kernel premise is proven end-to-end and
   everything after this is assembly work. (If the panel driver source is
   missing from the current `display-drivers` build, this test fails with a
   black screen – which is itself the diagnostic; see §7.1.)
   Note the asymmetry of risk: do **not** run the inverse experiment of booting
   the unmodified gts9wifi recovery on the Ultra – wrong-panel init sequences
   from a mismatched overlay are usually tolerated but there's no upside to
   finding out.

### Phase 1 – Kernel + techpack deltas

1. Diff Samsung X910 drop vs X710 drop (core kernel + each techpack). Expected
   result: a handful of `sec` input/display/audio source dirs and Kconfig
   fragments.
2. Decision point – two options:
   - **A (preferred): single family tree.** Merge the Ultra-only sources +
     Kconfig into the existing `kernel-samsung-gts9wifi` and techpack forks,
     keeping one kernel binary for both devices (mirrors Samsung's own family
     tree and the NinjaSU precedent; halves future maintenance).
   - **B: parallel `kernel-samsung-gts9uwifi` tree** with the ~40 halium
     commits rebased. Cleaner provenance, double maintenance.
3. Enable the Ultra's touch IC and panel configs as modules; confirm they land
   in the DLKM output set.

### Phase 2 – Vendor / super for the Ultra

1. Determine the gts9wifi firmware-tarball edit set: mount each tarball image
   and diff against pristine stock X710 partitions of the matching build.
   Expected candidates: fstab tweaks, disabled services, SELinux-adjacent
   touches; possibly nothing beyond repacking.
2. Apply the identical edit set to stock X910 partitions →
   `ubuntu-touch-kalama-firmware-gts9u.tar.xz`; host alongside the existing one.
3. `swap-vendor-modules.sh` runs unchanged (it swaps by filename inside
   vendor_dlkm erofs and preserves SELinux contexts; the Ultra's stock
   vendor_dlkm will contain its own touch/panel .kos, which get replaced by the
   halium-built equivalents where names match – verify the Ultra-only modules
   are all rebuilt in Phase 1 so no stale-ABI stock .ko remains load-bearing).

### Phase 3 – Rootfs overlay + deviceinfo

1. Port every `overlay/` file per §3.3: the `gts9uwifi.yaml` deviceinfo (14.6"
   physical size, 2960×1848, DPI ≈ 239, notch geometry if Lomiri's notch/cutout
   support is to be used – see §7.4), audio policy XMLs lifted from X910 stock
   vendor, sensorfw, repowerd waits, EFS units.
2. `deviceinfo` edits per §3.3; keep `kalama-gki_defconfig halium.config`.
3. CI: new job/variables for the second codename; artifact naming.

### Phase 4 – Install flow + validation ladder

1. Odin: Ultra recovery.tar (+ vbmeta) → TWRP → adb sideload the gts9uwifi zip.
2. Ladder: (a) recovery UI + touch (already proven in Phase 0), (b) UT boots to
   Lomiri – display modeset at 2960×1848, (c) subsystem sweep in order:
   touch/gestures → Wi-Fi (`wlan0`, MAC conf) → GPU/hybris (Lomiri smooth,
   `test_egl`) → audio (4 speakers, policy routing) → sensors (rotation, ALS) →
   S Pen hover/pressure → battery/charging telemetry (sec-battery on 11200 mAh
   pack) → BT → microSD → external display over USB-C DP alt-mode → cameras →
   fingerprint (last).
3. Regression guard: re-run the same build for gts9wifi and verify no X710
   regressions if Option A (single tree) was chosen.

| Feature | Expectation | Basis |
|---|---|---|
| Display 2960×1848 @120 Hz | High, once panel source confirmed | Stock DTBO + ss_dsi driver; SDE handles the mode; notch is a UI question not a bring-up question |
| Touch | High | Stock DTBO + correct first-stage module; the only work is identifying/building the Ultra's driver |
| GPU (Adreno 740, hybris) | High | Identical SoC; already working on X710 |
| Wi-Fi / BT | High | Same qca6490-class chip, same techpacks |
| Audio (quad speakers) | High | Cirrus amps present family-wide; needs Ultra audio-policy XMLs |
| Sensors | High | adsp_factory stack family-wide + sensorfw conf |
| S Pen | High | Same digitizer stack via stock vendor + DTBO |
| Battery/charging (45 W) | High | sec-battery/sm5714/sm5440 family-wide; params from stock DT |
| microSD, USB, OTG | High | Already patched heavily on X710 (usb_notify/dwc3 stack) |
| External display (DP alt-mode) | Medium | dp driver + lt9611/redriver modules present; UT-side support is the variable |
| Camera – main rear + main front | Medium | vendor HAL from X910 stock exposes them; UT camera stack (qtubuntu-camera fork exists in the group = active WIP) is the bottleneck. Check what camera state the X710 build is actually in today – the Ultra will match it at best |
| Camera – rear UW + front UW | Low without extra work | Aux/logical cameras are typically hidden by Samsung's HAL from the IDs UT enumerates; exposing them means HAL config surgery or vendor-tag plumbing. Do not promise this |
| Fingerprint (under-display optical) | Low/stretch | biometryd integration on Samsung optical UDFPS is its own project; a biometryd fork exists in the group, so rails are there |
| Notch-aware UI | Cosmetic/medium | Lomiri cutout handling exists but needs per-device geometry; otherwise the notch just occludes a strip of the front-UW corner |

## 7. Risks and open questions

1. **Panel driver source (display-drivers).** Samsung's ss_dsi panel support is
   per-panel C tables/config inside the display techpack. If the X710 drop that
   Azkali's `display-drivers` fork is based on does not include the Ultra's
   panel, the Phase 0 keystone test shows a dead panel and the fix is importing
   the panel dir + Kconfig from the X910 drop. Bounded, mechanical work – but it
   is the most likely first blocker.
2. **Touch IC identity.** Unknown until stock X910 `modules.load` is read
   (Phase 0.3). If it's another STM FTS variant the driver may even share source;
   if it's a different vendor, import from the X910 drop.
3. **Base DTB divergence.** Likely identical (common-kalama scheme), but if the
   Ultra base DT differs (e.g., larger cont_splash carveout for 2960×1848,
   memory map), regenerate `vendor_dts` from X910 stock. Phase 0.2 settles it
   cheaply. Related: the cont_splash reclaim experiment was reverted at HEAD –
   leave it reverted for the Ultra too.
4. **Notch.** The front-UW camera lives in a display cutout. Bring-up is
   unaffected; UI polish needs cutout geometry in the device config.
5. **Firmware-tarball edit set is undocumented.** Mitigated by the diff-and-
   replicate approach (Phase 2.1). Worst case, ask Azkali – the `q2q/edit_vendor`
   repo shows his prior pattern for the Fold 3 and suggests the edits are
   scripted and small.
6. **Recovery/super partition sizes on X910.** Verify from PIT before building;
   `deviceinfo_recovery_partition_size` and `SUPER` in `super.sh` are hardcoded
   to X710 values (109576192 / 11643387904).
7. **2.x splash-hang provenance.** The revert at kernel HEAD suggests the
   2026-07-29 build fixed it, but confirm on the X710 before anchoring the Ultra
   port to this base – debugging a known-regressed base on new hardware would
   conflate two problems.
8. **Anti-rollback / SPL.** Keep custom image SPL (2025-05) ≥ the level implied
   by the installed stock, or refresh `deviceinfo_bootimg_os_patch_level` when
   building against newer donor firmware.
9. **Odin vs Heimdall on this generation.** Verify Heimdall protocol support for
   SM8550-era Samsung download mode before relying on a Linux-only bench.
